왜 이렇게 했나

1. 진입점을 둘로 나눴다 — 생성자는 그대로

CoFaker(locale:) 는 소문자화와 - → _ 만 하고 언어는 첫 _ 앞이다. 이 규칙을 더 똑똑하게 고치면(.UTF-8 제거, 스크립트 무시) 기존 사용처의 출력이 달라질 수 있다 — 특히 zh_TW 는 지금 중국어(간체) 데이터를 받고, ja_JP.UTF-8 는 ja 언어 전용 데이터로 폴백한다. 그래서 생성자는 건드리지 않고, 새 규칙은 resolve/forLanguage 에만 두었다. faker.language 도 생성자가 데이터 선택에 쓰는 것과 같은 규칙(locale 의 첫 _ 앞)으로 파생한다.

버린 대안: 생성자 정규화 개선 — 바이트 동일 계약(#55)을 깰 위험이 있고, 이 Story 의 AC("생성자의 출력은 바뀌지 않는다")와 충돌한다.

2. 언어 → 국가 로케일, 폴백은 en_us

이슈의 매핑 그대로 ko→ko · en→en_us · zh→zh_cn · ja→ja_jp · de→de_de · fr→fr_fr · ru→ru_ru · it→it_it · pt→pt_br. 지원 밖 언어와 번체는 영어 언어의 국가 로케일(en_us)로 폴백한다 — forLanguage('en') 과 같은 풍부한 데이터이고, 이 Story 의 존재 이유("얇은 언어 데이터가 아니라 국가 데이터")와 일관된다.

버린 대안: 폴백을 얇은 en 로케일로 — 영어 설정과 지원 밖 설정이 서로 다른 영어 데이터를 받게 된다.

3. 번체 규칙은 co_demo_prefs 와 같게, 의존은 없이

DemoLocale.parse 와 같은 집합(hant · tw · hk · mo 이면 거부, 스크립트 Hans 면 지역과 무관하게 간체)을 co_faker 안에 같은 의미로 구현했다. co_faker 는 co_demo_prefs 에 의존하지 않는다 — 규칙만 맞췄다. 테스트가 데모 로케일 태그 10종(ar 제외)이 지원으로 읽히는지 확인한다. 한 곳만 다르다: BCP-47 확장(-u-)과 사적 사용(-x-) 뒤의 서브태그는 읽지 않는다(zh-CN-x-hk 가 번체로 거부되지 않게 — 리뷰 지적).

4. es 는 지원 + 기본 모듈만

이슈의 "기존 es 는 기본 모듈만 지원하는 언어로 등록"을 supported == true · domain == false · 로케일 es(국가 로케일이 없어 언어 전용 로케일 그대로)로 읽었다. 레지스트리에 있는 언어는 전부 "지원"이고, 도메인 데이터 유무는 domain 이 따로 말한다.

5. 지역은 읽기만 한다

resolve 는 region(CN · 419 등)을 보고하지만 로케일 선택에는 쓰지 않는다 — en-GB 는 en_us, pt-PT 는 pt_br. 이슈의 매핑이 언어 단위이고, S2 의 도메인 번들도 언어 키이며, 기존 CoFaker(locale: 'pt_PT') 도 이미 브라질 데이터이기 때문이다. 특정 국가가 필요하면 CoFaker.forCountry 가 있다. region 이 이미 노출돼 있어 나중에 지역 인식 선택을 API 변경 없이 얹을 수 있다.

6. domain 은 한 곳의 조회 — S2 가 교체

CoFakerLanguage.domain 은 언어마다 달린 플래그가 아니라 파일 맨 아래 비공개 함수 _hasDomainData(code) 하나를 읽는다. 지금은 ko · en 만 true 이고, 그 함수의 주석에 "S2 가 도메인 번들 레지스트리 계산으로 교체한다"고 적어 두었다. 레지스트리 항목에는 domain 인자가 없으므로, 이후 언어 Story 가 레지스트리를 고칠 일이 없다. 테스트도 ko/en 은 true, es 는 false 만 단언하고 나머지 언어는 단언하지 않는다 — 언어 Story 가 도메인 데이터를 넣을 때 이 테스트가 깨지지 않게 하려는 것이다.

7. 이슈가 이름을 주지 않은 타입

이슈 본문은 CoFakerLanguages · CoFaker.language · CoFaker.forLanguage · supported · domain 만 정한다. 나머지는 CoFakerCountries/CoFakerCountry 규약에 맞춰 정했다: 레지스트리 항목 CoFakerLanguage(code · locale · script · domain), resolve 결과 CoFakerLanguageResolution(language · supported · region · locale), 문자 체계 CoFakerScript(latin · han · kana · cyrillic · hangul). 그 밖의 공개 멤버(byCode 같은 조회, 태그 파서)는 만들지 않았다.

8. 사용자 지정 locales

forLanguage 는 locales 를 생성자에 그대로 넘긴다. 따라서 해석된 로케일 코드(ja_jp)로 조회되고, 언어 코드(ja)로 등록한 사용자 로케일은 내장 국가 로케일에 가려진다 — dartdoc · README · 테스트에 적었다. CoFaker(locale: 'ja', locales: {'ja': custom}) 는 전과 같이 동작한다.

후속 Story 가 알아야 할 것

  • faker.language 는 locale 에서만 파생되므로 CoFaker(locale: 'zh_TW') 는 zh 로 보고된다(데이터도 기존처럼 중국어). S2 가 faker.language 로 번들을 조회하면 이 코드들은 간체 도메인 문구를 받게 된다. "번체 독자에게 간체를 주지 않는다"를 도메인 문구에도 적용하려면 S2 에서 조회 전에 CoFakerLanguages.resolve(faker.locale).supported 를 확인하거나, 생성자의 zh_TW 출력 유지 계약과 어떻게 맞출지 정해야 한다.
  • 생성자는 ja_JP.UTF-8 를 ja_jp.utf_8 로 두고 ja 언어 전용 데이터로 폴백한다(ja.UTF-8 처럼 _ 가 없으면 영어, faker.language 는 ja.utf). 둘 다 기존 동작 그대로이고, ja_JP.UTF-8 쪽은 테스트로 고정했다.
  • S4 의 언어 커버리지 표는 CoFakerLanguages.all(10종)과 CoFakerLanguage.domain 을 읽으면 된다.
